# e'llipse — модернизация сайта

Полная модернизация сайта сети магазинов парфюмерии и косметики **e'llipse** (Томск, Северск, Новокузнецк, Кемерово): сайт полностью переписывается с Bitrix на новый стек — Vue 3 SPA на фронте, FastAPI-сервисы на бэке.

Документ объединяет документацию по всем частям проекта: архитектуру, backend, frontend, инфраструктуру, скрипты и текущий статус готовности к продакшену.

---

## 1. Архитектура проекта

Четыре независимых компонента, каждый — отдельный git-проект / Docker-контейнер(ы):

| Компонент | Назначение | Порт (dev) |
|---|---|---|
| `ellipse-back` | Основной backend: каталог, магазины, акции, публичное API для фронта | 8000 |
| `ellipse-sync` | Тонкий сервис-прокси для синхронизации остатков/цен с 1С | 8001 |
| `ellipse-front` | Vue 3 SPA (Pinia, Vue Router, Swiper) | 5173 (dev) |
| `ellipse-nginx` | Реверс-прокси + HTTPS (Let's Encrypt) поверх всех трёх | 80/443 |

`ellipse-back` и `ellipse-sync` физически разделены осознанно — разный жизненный цикл деплоя, `ellipse-sync` не имеет доступа к БД напрямую и ничего не резолвит сам, а просто пересылает запросы в `ellipse-back` через internal API с общим секретом.

## 2. Стек технологий

**Backend:**
- Python 3.13, FastAPI, SQLAlchemy 2.0 (async), asyncpg, Pydantic v2
- PostgreSQL (+ `pg_trgm` для поиска с опечатками)
- Хранилище изображений: абстракция `local` (диск сервера) / `s3` (Timeweb Cloud или совместимое)
- Docker Compose, Nginx, Let's Encrypt (Certbot)

**Frontend:**
- Vue 3 + Composition API (`<script setup>`)
- JavaScript (без TypeScript)
- Vite, Vue Router, Pinia
- CSS Variables — вся палитра и типографика через кастомные свойства, никаких «магических» значений в компонентах
- Swiper — слайдеры/галереи
- 2ГИС RasterJS API — интерактивные карты

## 3. `ellipse-back` — основной backend

### 3.1. Структура (feature-based модули)

```
app/
├── core/
│   ├── config.py       # настройки (.env)
│   ├── database.py     # async SQLAlchemy engine/session
│   └── storage.py       # абстракция хранилища изображений (local/S3)
├── modules/
│   ├── catalog/         # Brand, Category, Product, ProductImage, ProductPrice, Inventory
│   ├── stores/          # Store, StoreImage
│   ├── promotions/      # Promotion, PromotionProduct
│   ├── storefront/       # публичный агрегирующий API для фронта
│   └── sync/             # internal API для ellipse-sync
└── main.py
```

Разделение: `catalog`/`stores`/`promotions` — «чистые» CRUD-модули по сущностям (для админки/наполнения данных). `storefront` — отдельный слой, который **агрегирует** данные из всех трёх модулей в удобные для фронта ответы (не дублирует CRUD, а собирает поверх них).

### 3.2. Модель данных

Таблицы: `brands`, `categories` (self-referencing дерево, произвольная глубина), `products`, `product_images`, `product_prices`, `stores`, `store_images`, `inventory`, `promotions`, `promotion_products`.

**Важное архитектурное решение по ходу проекта:** цена товара изначально была привязана к товару глобально (`product_prices.product_id`). После изменения бизнес-требований переделано — **цена теперь за парой (товар, магазин)** (`product_prices.store_id`), у каждого магазина своя цена на один и тот же товар. Миграция `scripts/migrate_prices_to_stores.py` добавляет колонку и **удаляет старые обезличенные цены** (они больше не имели смысла в новой модели).

### 3.3. Публичный API (`storefront`, для фронтенда)

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/products` | Каталог с пагинацией, поиском, фильтрами (`category_id`, `brand_id`, `is_hit`, `min_price`/`max_price`), сортировкой |
| GET | `/api/products/{id}` | Карточка товара: бренд, категория с полным путём (хлебные крошки), картинки, акции, **таблица цена+наличие по каждому магазину** |
| GET | `/api/products/hits` | Товары-хиты для главной |
| GET | `/api/products/categories` | Дерево категорий (рекурсивное, произвольная глубина) |

**Поиск** (`search=`) — комбинация двух механизмов PostgreSQL в одном запросе: полнотекстовый поиск с русской морфологией (понимает словоформы: «крем»/«крема»/«кремы») + `pg_trgm` по похожести (прощает опечатки: «тоналный» → «тональный»), сортировка по релевантности. Индексы создаются `scripts/setup_search.py`.

**Фильтр по категории** учитывает **всё поддерево** — фильтр по родительской категории находит товары и во всех вложенных подкатегориях, а не только с точным совпадением `category_id`.

**Фильтр по цене** — товар подходит, если **хотя бы в одном** магазине его текущая цена попадает в диапазон (после перехода на цены по магазинам).

Карточки в каталоге не показывают числовую цену вообще (у товара их несколько, по одной на магазин) — вместо этого фронт показывает фразу «Узнать цену и количество»; полную таблицу цена/наличие по магазинам показывает страница товара.

### 3.4. CRUD-эндпоинты (`catalog`, `stores`, `promotions`)

Полный CRUD (`GET`/`POST`/`PATCH`/`DELETE`) для: `categories`, `brands`, `products`, `product-images`, `product-prices`, `inventory`, `stores`, `store-images`, `promotions`, `promotion-products`.

**Авторизация.** `GET` публичны. Любой метод записи (`POST`/`PATCH`/`PUT`/`DELETE`) требует заголовок `Authorization: Bearer <ADMIN_API_TOKEN>`; без него — 401, а если токен не настроен — 503 (запись отключена). Защита навешена на уровне роутера (`require_admin_for_writes`), поэтому новые методы записи защищаются автоматически; тест обходит все маршруты приложения и проверяет это.

### 3.5. Internal API и синхронизация с 1С

- `POST /internal/sync/inventory-prices` (заголовок `X-Internal-Api-Key`) — принимает уже нормализованную пачку от `ellipse-sync`: `{items, rejected, batch_id, mode, final, stores, raw}`. Резолвит `external_id → UUID`, массово (`INSERT … ON CONFLICT`) обновляет `inventory`, а **новую строку в `product_prices` добавляет только если цена изменилась** — история цен не раздувается. Несопоставленные товары/магазины не роняют пачку, а копятся в `sync_unmatched` со счётчиком.
- Режим `mode=full` (+ `batch_id`, `final=true` в последней пачке): после последней пачки остаток товаров, которых в выгрузке не было, обнуляется (только для магазинов этой выгрузки).
- Журнал: таблицы `sync_log`, `sync_unmatched`, `sync_session`. Сырое тело запроса хранится по политике `SYNC_STORE_RAW` (`all` / `errors` / `none`).
- Лимит пачки — `MAX_SYNC_BATCH_ITEMS` (по умолчанию 2000, при превышении 413).
- Мониторинг (Bearer `ADMIN_API_TOKEN`): `GET /admin/sync/status` (последняя успешная синхронизация, счётчики за 24 ч), `/admin/sync/log`, `/admin/sync/log/{id}`, `/admin/sync/unmatched`.
- Снаружи `/internal/*` закрыт в nginx (404): sync ходит к backend по docker-сети.

### 3.6. Хранилище изображений

`app/core/storage.py` — интерфейс `ImageStorage` с двумя реализациями:
- `LocalStorage` — диск backend-сервера, отдаётся через смонтированный `/media` (FastAPI `StaticFiles`)
- `S3Storage` — S3-совместимое хранилище (Timeweb Cloud), через `boto3`

Переключение — одна переменная `STORAGE_BACKEND=local|s3` в `.env`, код менять не нужно.

### 3.7. Скрипты (`scripts/`)

| Скрипт | Назначение |
|---|---|
| `seed_data.py` / `clear_seed_data.py` | Наполнение БД тестовыми данными для разработки / их безвозвратное удаление (по префиксу `seed-` в `external_id`, не трогает остальные данные) |
| `import_brands.py` | Импорт брендов из CSV-выгрузки старого сайта (Bitrix), upsert по `external_id` |
| `import_products.py` | Импорт товаров из CSV, резолвит бренд/категорию, создаёт первую картинку |
| `import_store_images.py` | Импорт фото магазинов из папок `<id_магазина>/фото...` — папка полностью заменяет набор фото магазина при каждом запуске |
| `import_promotion_banners.py` | Импорт баннеров акций (один файл на акцию), сопоставление по `id`/`external_id` |
| `migrate_images.py` / `migrate_store_images.py` | Перенос уже скачанных файлов (по старым «мёртвым» путям в БД) в активное хранилище (local/S3), сопоставление по имени файла |
| `migrate_prices_to_stores.py` | Миграция схемы `product_prices` на модель «цена за магазином» (см. 3.2) |
| `setup_search.py` | Включение `pg_trgm`, создание индексов поиска. Теперь это делают миграции Alembic; скрипт оставлен для старых баз |
| `map_store_external_ids.py` | `--export` — выгрузить магазины в CSV, `--apply` — загрузить из CSV GUID-ы магазинов из 1С (`external_id`), с проверкой дублей, `--dry-run` |
| `preprocess/preprocess_products.py` | Единый пайплайн: `unloading.csv` (+ `marja.xls`) → `products_ready.csv` для `import_products.py`; отчёты об отбракованных строках и неизвестных категориях. См. `scripts/preprocess/README.md` |

Все скрипты идемпотентны (upsert или явные проверки «уже сделано») — можно запускать повторно без дублирования данных.

## 4. `ellipse-sync` — сервис синхронизации с 1С

Отдельный сервис-адаптер: `POST /sync/inventory-prices` от 1С → **терпимая нормализация** → пересылка в `ellipse-back` (internal API) → отчёт обратно. В БД не пишет.

Реальный формат выгрузки 1С пока неизвестен, поэтому нормализатор (`app/modules/inventory_prices/normalizer.py`) принимает «неряшливые» данные: имена полей латиницей и кириллицей (алиасы; дополняются файлом `FIELD_ALIASES_FILE`), числа строкой с запятой и пробелами, GUID в любом регистре / в скобках / без дефисов, тело-список или объект с массивом в `items`/`Товары`/…, магазин на уровне пачки или группы, UTF-8 и cp1251. Нераспознанные строки не роняют пачку: они попадают в `rejected` с причиной и в журнал. Если формат окажется другим — правится один файл.

Три **разных** секрета: `SYNC_API_KEY` (1С → sync; принимается как `X-Api-Key`, `Bearer` или `Basic`, пароль = ключ), `INTERNAL_API_KEY` (sync → back), `ADMIN_API_TOKEN` (админские операции). `GET /sync/status` — когда была последняя успешная синхронизация.

Спецификация для программиста 1С — [docs/1C_INTEGRATION.md](docs/1C_INTEGRATION.md). Эмулятор 1С для проверки без реальной 1С — `ellipse-sync/tools/mock_1c.py`.

## 5. `ellipse-nginx` — реверс-прокси и HTTPS

Три поддомена на одном сертификате Let's Encrypt:

- `example.com` (`www` → редирект на без-www) → статика фронтенда
- `api.example.com` → `ellipse-back` (+ `/media/`; `/internal/` закрыт)
- `sync.example.com` → `ellipse-sync` (сюда стучится 1С)

Домен задаётся одной переменной `DOMAIN` в `ellipse-nginx/.env` (шаблоны nginx подставляют её сами). Есть gzip, security-заголовки, кэш статики и `/media/`, ограничение частоты запросов (api 20 r/s, sync 5 r/s), запуск nginx не зависит от того, поднят ли backend (адреса резолвятся при запросе).

Первый запуск — `init-letsencrypt.sh` (временный HTTP-конфиг → сертификат → HTTPS). Продление — контейнер `certbot`. Сайт собирается `build-frontend.sh` (Node на сервере не нужен). Пошаговая инструкция — [DEPLOY.md](DEPLOY.md).

## 6. `ellipse-front` — клиентская часть

### 6.1. Запуск проекта

```bash
npm install
npm run dev      # локальная разработка
npm run build    # сборка в продакшн
```

### 6.2. Переменные окружения

Создай файл `.env` в корне проекта:

```
VITE_2GIS_API_KEY=твой_ключ_2ГИС
VITE_API_BASE_URL=http://localhost:8000
```

- `VITE_2GIS_API_KEY` — без него компонент карты (`MapEmbed`) не сможет отрисовать карту, ключ обязателен для 2ГИС RasterJS API. Получить можно в личном кабинете разработчика 2ГИС.
- `VITE_API_BASE_URL` — адрес `ellipse-back`. Локально — `http://localhost:8000`, в продакшене — `https://api.example.com` (см. раздел 5 про поддомены в `ellipse-nginx`).

### 6.5. Ключевые UI-компоненты

#### `BaseButton`
Единая кнопка на весь проект — **все** кликабельные элементы (кнопки и ссылки-кнопки) должны использовать её, а не голые `<button>`/`<a>`.

Пропсы:
- `tag` — `button` | `a` | `router-link` (+ `href`/`to`)
- `color` — `black` | `gold` | `pink` | `accent`
- `size` — `sm` | `md` | `lg`
- `shape` — `default` | `pill` | `circle` | `block`
- `variant` — `solid` | `outline` | `ghost`
- `active` — состояние выбранного таба (с `variant="ghost"`, например категории `MegaMenu`)
- нативный `disabled` тоже поддерживается (проп прокидывается как обычный HTML-атрибут)

`outline` и `ghost` зависят от `color`/контекста (тёмный `gold` для Header/Footer, светлый `pink` для карточек на белом/пастельном фоне) — при добавлении нового цветового контекста может понадобиться доопределить стили для него.

#### `BaseInput`
Аналогично — базовый инпут с `color`/`size`/`placeholder`.

#### `CitySelect`
Самодостаточный: сам берёт город и список городов из `stores/city.js`, сам вызывает `selectCity()` при изменении. Не требует пропсов/`v-model` — просто `<CitySelect />` в любом месте.

#### `MapEmbed`
Обёртка над 2ГИС RasterJS API (`DG.map`). Пропсы: `lat`, `lon` (обязательные), `zoom`, `height`, `apiKey` (по умолчанию из `VITE_2GIS_API_KEY`), `aria-label`. Реагирует на смену координат (перецентровка + маркер), поэтому безопасно переиспользовать при переключении между объектами (магазинами и т.п.).

#### `ImageSlider`
Универсальная галерея на Swiper (стрелки + пагинация) для фото без текстовых оверлеев — в отличие от `PromoSlider`, который заточен под полноэкранные баннеры с заголовками. На странице товара (`ProductView`) для главного фото используется не он, а обычный `<img>` — там нужна одна статичная картинка, а не слайдер.

#### `PhotoGallery` *(новый)*
Переиспользуемая галерея с порогом «сетка/слайдер»: если фото ≤ `gridThreshold` (по умолчанию 3) — CSS-сетка, если больше — слайдер на Swiper (стрелки + точки). Используется на странице магазина; можно переиспользовать где угодно, где число фото заранее не известно.

#### `HeaderSearch` *(новый)*
Поиск, вынесенный из `Header` в отдельный компонент. Форма с `@submit.prevent`, работает и по Enter, и по клику на иконку-лупу. При отправке — переход на `/catalog?search=...`, синхронизируется с URL в обе стороны.

#### `PromoSlider`
Слайдер акций на главной. **Фиксированное соотношение сторон 1920:600** — баннеры нужно готовить именно под это разрешение (или кратное), иначе изображение будет обрезано/растянуто непредсказуемо.

#### `FeedbackForm`
Форма обратной связи (имя, контакт, сообщение) с обязательным чекбоксом согласия на обработку персональных данных — кнопка отправки задизейблена, пока чекбокс не отмечен. Используется на `ContactsView` и `CareerView`. **Не подключена к backend** — только показывает сообщение об успехе локально (см. раздел 6.9).

### 6.6. Layout-компоненты

- **`Header`** — sticky, 3 строки (город+лого / каталог+поиск+иконки / навигация), адаптивный (на узких экранах трансформируется из горизонтального в вертикальный layout). Поиск вынесен в отдельный `HeaderSearch`.
- **`Footer`** — информационный, 4 колонки + золотая линия сверху.
- **`MegaMenu`** — выпадает из кнопки «Каталог», вынесен через `Teleport` в `<body>` (чтобы не зависеть от stacking context/overflow родителей), закрывается по клику вне себя и при смене роута. Категории берутся из `stores/catalog.js`, дерево приходит с backend **как есть** (`{ id, name, children: [...] }`, рекурсивно, произвольная глубина — не фиксированные «большая/малая подкатегория», как было на старте проекта до интеграции с backend).
- **`CityModal`** — модалка выбора города при первом визите (пока город не выбран в `localStorage`).
- **`CookieConsent`** — баннер согласия на cookie, тоже на `localStorage`.

⚠️ И `CityModal`, и `CookieConsent`, и вызов `cityStore.init()` нужно подключить в `App.vue` вручную (см. историю чата/комментарии в самих файлах) — в этом README не дублирую точный код, чтобы не разойтись с актуальным `App.vue`.

### 6.8. Pinia-сторы

| Стор | Что хранит |
|---|---|
| `home.js` | Хиты продаж на главной — реальный запрос к `/api/products/hits` |
| `catalog.js` | Категории (дерево произвольной глубины с backend) + товары каталога с пагинацией, поиском и фильтрами — реальные запросы к `/api/products*` |

### 6.9. Известные ограничения / TODO

- **Корзина, избранное, личный кабинет** — только кнопки-заглушки в `Header`/`ProductView`, логики нет. Backend для этого тоже пока не реализован (см. раздел 8).
- **Акции: часть маркетинговых полей не хранится в backend** — `slug`, `kind`, `isFeatured`, `priority`, `buttonText`, `buttonLink`, `conditions`, `productIds` есть только в старой мок-модели, в БД их нет. `getPromotionBySlug` всегда вернёт `undefined`, `featuredPromotions` не сортирует по приоритету (просто отдаёт все опубликованные). Нужно решить: добавлять в БД или убирать из фронта.
- **Товар: состав/отзывы** — `composition`/`reviews` на `ProductView` — заглушки (backend не хранит состав, отзывов как функциональности вообще нет).
- **Страница политики обработки персональных данных** — отдельной страницы нет, чекбокс согласия и cookie-баннер временно ссылаются на `/about`.
- **Отправка форм** (`FeedbackForm`) — не подключена к backend, только показывает сообщение об успехе локально; на backend нет соответствующего эндпоинта.
- **2ГИС API-ключ** — нужно прописать самостоятельно в `.env` (см. раздел 6.2).

### 6.10. Соглашения по работе с проектом

- Каждый компонент — одна логическая задача; не дробить на десятки мелких без необходимости и не объединять разное в один компонент.
- Все цвета — только через CSS-переменные, никаких хардкод-хексов в компонентах.
- Новую функциональность реализовывать по мере запроса, не забегать вперёд.
- Если для правки нужно менять несколько файлов — сначала явно перечислить их.

## 7. Тестирование

**ellipse-back** (`pytest`, 37 тестов, нужен PostgreSQL): `pip install -r requirements-dev.txt && pytest`. Фикстура сама пересоздаёт БД `ellipse_test` и прогоняет `alembic upgrade head`. Покрыто: все маршруты записи без токена → 401, валидация production-конфига, синхронизация (цена пишется только при изменении, частичные обновления, несопоставленные товары, полная выгрузка с обнулением, политика хранения raw, журнал при исключении, статус, уникальность `external_id`, пачка в 1500 строк).

**ellipse-sync** (`pytest`, 19 тестов, БД не нужна): нормализатор (кириллица, запятые, GUID, вложенные группы, cp1251) и API (авторизация тремя способами, 400/413/422/502).

**Эмулятор 1С**: `ellipse-sync/tools/mock_1c.py` — сценарии clean / sloppy / cyrillic / grouped / bad / notjson / cp1251 / full / load / status, чтобы проверить сервис до готовности настоящей выгрузки.

`test_sync_service.ipynb` — старый ноутбук с ручными проверками синхронизации (оставлен как справочный; актуальные проверки — в `pytest`).

Frontend автотестов не имеет; `npm run lint` и `npm run build` проходят чисто.
